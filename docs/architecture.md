# SEG Runtime Architecture

SEG's runtime architecture is documented as a small, evidence-backed system model rather than a hand-maintained flowchart.

![SEG runtime architecture — dark preview](architecture/seg-architecture-dark.svg)

The dark static preview above is derived from the same validated model in [`docs/architecture/seg.architecture.json`](architecture/seg.architecture.json). [Archify](https://github.com/tt-a1i/archify) remains the canonical renderer for release evidence. The committed source stays repository-portable so it survives SEG's clean public export; CI injects the current repository URL and exact commit SHA into a temporary copy before validation, giving each generated evidence bundle explicit provenance without baking private workshop history into the public package.

The full interactive HTML, light/dark captures, validation receipt, and browser visual-check evidence are regenerated by the **Validate Architecture Evidence** GitHub Actions workflow and uploaded as a workflow artifact. The generated HTML is intentionally not committed to keep the repository lean.

## Core flow

```text
Target Skill / Caller
        |
        v
SEG Entry Points
        |
        v
Evaluation DAG
        |
        v
Evidence Join
        |
        v
Multi-Gate Oracle
        |
        +---- ACCEPT / ESCALATE ----> Evidence Artifacts
        |
        +---- REVISE ----> Repair Sandbox ----> re-evaluate candidate

Target Skill ---- optional live benchmark ----> Live Behaviour ----> Evidence Artifacts
```

### SEG Entry Points

The CLI and agent-facing entry points establish the Target Skill, evaluation scope, and execution mode. The main entry points are:

- `plugins/skill-evaluation-graph/scripts/audit_skill.py` — deterministic evaluation/reporting over the canonical engine;
- `plugins/skill-evaluation-graph/scripts/run_loop.py` — bounded evaluation and Repair Iteration;
- `plugins/skill-evaluation-graph/scripts/eval_skill.py` — static behavioural policy analysis and optional live trials.

### Evaluation DAG

`plugins/skill-evaluation-graph/src/seg/graph.py` executes the real Evaluation Graph. The default graph contains seven evaluator nodes and runs independent work in dependency-aware waves.

**Wave 1**

- Schema
- Links & Syntax
- Safety & Privacy
- Portability

**Wave 2**

- Trigger Routing
- Token Economics
- Behavioural Policy Coverage

Every Node Result records status, duration, Findings, metrics, Evidence, input digest, and output digest. Failed required Evaluators fail closed rather than being treated as missing data.

### Evidence Join

The Evidence Join in `plugins/skill-evaluation-graph/src/seg/oracle.py` aggregates Node Results into `JoinedEvidence`. It keeps observations, Findings, provenance, and quality metrics available to the decision layer instead of collapsing everything into one score.

### Multi-Gate Oracle

The Oracle evaluates explicit Mandatory Gates and returns one canonical Verdict:

- `ACCEPT`
- `REVISE`
- `ESCALATE`

The default Mandatory Gates are:

1. `evaluation_integrity`
2. `specification_conformance`
3. `safety_privacy`
4. `link_integrity`
5. `quality_policy`

A high Static Quality Score cannot compensate for a failed conformance, integrity, safety, or link gate.

### Repair Sandbox

`REVISE` can enter the Repair Iteration. Repair Proposals are applied to an isolated candidate, re-evaluated, and compared with the baseline before any target mutation is allowed.

The Repair Sandbox is inside an explicit **Mutation Boundary**:

- mutation is opt-in;
- candidate verification happens before target mutation;
- Mandatory Gate regressions reject the candidate;
- authorized mutation is rollback-protected.

### Live Behaviour

Live Behaviour is deliberately separate from the static Evaluation DAG.

The behavioural runner executes versioned scenarios in Control and Treatment arms, records valid/invalid Trials, and measures observable compliance, uplift, rationalisation markers, latency variance, and harness failures. Static behavioural policy analysis is not presented as a substitute for this live evidence.

### Evidence Artifacts

SEG produces evidence artifacts rather than only a headline score:

- tamper-evident SHA-256 Evaluation Receipts;
- evidence-backed scorecards;
- Oracle decisions and Gate results;
- Repair Iteration history;
- optional live Trial evidence.

See [`plugins/skill-evaluation-graph/references/terminology.md`](../plugins/skill-evaluation-graph/references/terminology.md) for the canonical meaning of Evaluation Graph, Evidence, Finding, Gate, Oracle, Repair Candidate, Seam, and Boundary.

## Architecture evidence

The committed Archify source is a **versioned architecture claim**, but it does not prove the implementation is correct by itself.

For CI validation, the workflow creates a temporary provenance-pinned copy of the source using the repository and commit currently under test. Archify then verifies a narrower and useful set of properties:

- referenced source paths exist in the exact checked-out revision;
- the architecture source conforms to the Archify schema;
- the diagram satisfies deterministic composition checks;
- delivery is reproducible for the pinned Archify version;
- browser containment and readability pass across the configured viewports and themes.

SEG's tests, source inspection, specification provenance, live-host evidence, and self-evaluation remain the authority for behavioural and implementation claims.

The baseline SEG architecture exercise used Archify `v2.16.0` against workshop runtime commit `b36bbdbf3fe87e52ff1f52ef089c37a22cb0a5fa` and passed:

- 9 / 9 deterministic architecture checks;
- 0 relationship crossings;
- 0 ambiguous corridors;
- 0 label-route clearance issues;
- 0 desktop readability issues;
- repository evidence verification across 16 source references;
- browser containment/readability checks from 1440×900 through 2048×1320 in light and dark modes.

## Reproducing the architecture artifact

The repository workflow pins the Archify release and checksum, adds exact revision provenance to a temporary specification, validates it, deterministically delivers the interactive HTML, performs browser visual checks, and uploads the resulting evidence bundle.

With Archify installed locally, the portable source can be checked directly against the current checkout:

```bash
archify validate architecture docs/architecture/seg.architecture.json \
  --quality showcase \
  --repo-root "$PWD"

archify deliver architecture \
  docs/architecture/seg.architecture.json \
  dist/architecture/seg-architecture.html \
  --quality showcase \
  --repo-root "$PWD"

archify visual-check dist/architecture/seg-architecture.html
```

When the runtime architecture materially changes, update the Archify source, rerun validation, inspect the browser captures, and update the committed dark preview. Do not change the diagram merely to make it prettier if the runtime model has not changed.
